# 启停与恢复

[[Ubuntu服务器/首页|← 运维中心]] · [[日常巡检]] · [[备份与升级]]

## 启动前置

```bash
findmnt /mnt/docker-data
systemctl is-active containerd docker
```

> [!danger] 前置失败
> 机械盘未挂载时不要强行启动 Docker，不要在 `/mnt/docker-data` 空目录创建数据。

## mall4cloud 启动顺序

### 第一层：数据服务

```bash
docker compose up -d \
  mall4cloud-mysql mall4cloud-redis mall4cloud-mongo \
  mall4cloud-minio mall4cloud-elasticsearch
```

等待 healthcheck 和应用级验证完成。

### 第二层：注册与消息基础

```bash
docker compose up -d \
  mall4cloud-nacos mall4cloud-rocketmq-namesrv mall4cloud-rocketmq-broker
```

### 第三层：上层中间件

```bash
docker compose up -d \
  mall4cloud-seata mall4cloud-job mall4cloud-canal \
  mall4cloud-rocketmq-dashboard mall4cloud-wukongim
```

## Java 服务顺序

```text
基础 Provider -> 依赖它的 Consumer -> 定时任务与网关
```

例如 Product 的库存任务依赖 Order Provider；Order 未注册时会出现 `invokers: 0`。

## AI 平台

### New API

```bash
cd /opt/1panel/apps/new-api/new-api
docker compose up -d
./update.sh
```

`update.sh` 会校验 Compose、在线拉取 `calciumion/new-api:latest` 并重建服务。

### Dify

```bash
cd /home/shadowdu/services/dify
docker compose up -d --pull never --remove-orphans
docker compose ps -a
```

Dify 正常状态为 15 个常驻服务运行，`init_permissions` 为 `Exited (0)`。
API 容器重建后如 Nginx 暂时返回 `502`，刷新内部 DNS：

```bash
docker compose restart nginx
```

首次冷启动会从机械盘加载较大的 Python 镜像，I/O wait 可能短时升高。

## 停止

```bash
cd ~/services/mall4cloud-middleware
docker compose stop
```

需要重建容器但保留数据：

```bash
docker compose down
docker compose up -d
```

> [!danger] 永久禁止
> 不执行 `docker compose down -v`。

同样禁止对 Dify 执行 `docker compose down -v`，避免删除 Compose 管理卷。

## 单服务恢复

1. 查看状态与最近日志。
2. 判断依赖是否先故障。
3. 仅重启目标服务。
4. 执行服务档案中的应用级验证。
5. 验证依赖方重连和任务补偿。

```bash
docker compose restart mall4cloud-nacos
docker logs --tail=200 mall4cloud-nacos
```

## 故障后的任务补偿

- Provider 恢复后确认 Dubbo 健康实例和 mapping。
- XXL-Job 失败任务按业务幂等性手动重跑。
- 库存游标、Canal 位点和 RocketMQ 消费位点必须先记录再修改。
